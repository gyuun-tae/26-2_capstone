항만공사 RAG 챗봇 전체 진행 계획 — 초안
====================================

작성일: 2026-09-11

**기획의 기준**

원본 과제는 「생성형AI 및 RAG 활용한 항만공사 챗봇 서비스 개발」이다. 민원인의 질문에 항만운영 서비스 소개, 대상, 법령, 업무추진 절차를 제공하고, 신속한 응답과 다국어 접근성, 반복 문의 대응 효율을 높이는 것이 제시된 방향이다. 출처: [과제 목록 원본](C:/Users/yountae/Downloads/산학협력캡스톤디자인프로젝트-과제-목록.xlsx), Sheet1!A5:C5.

확인된 팀 조건은 6명, 개발 기간 3개월, 실질적인 작업 빈도 주 1회, 전원 경진대회 1~2회 경험, 대상 기관 미정이다. 이를 약 12회의 공동 작업으로 계획한다. 개인별 추가 작업을 필수 전제로 잡지 않는다. 정확한 마감일, 회당 작업 시간, 주력 언어·프레임워크, 예산, 학교 평가표는 미정이다.

이하 기능 우선순위, 규모, 평가 목표는 기획 제안이며, 원본에 확정된 요구조건으로 적혀 있는 수치가 아니다. 일정은 주차별 회의 계획이 아니라 각 회차 안에 실제로 구현·통합·검토하는 작업 계획이다.

**1. 프로젝트 목표**

“선정한 항만공사의 공식 자료를 검색하여 민원인의 이용 대상·신청 절차·필요 서류 질문에 답하고, 답변의 근거 문서와 확인 기준을 함께 보여주는 웹 챗봇”을 개발한다.

RAG는 질문과 관련된 문서 부분을 먼저 찾고, 그 내용을 생성형 AI에 전달해 답변하도록 하는 방식이다. 본 프로젝트의 핵심 성과는 자료의 정확한 검색, 근거에 맞는 답변, 자료 변경 반영, 실제 사용자의 정보 탐색 시간으로 확인한다.

제안하는 개발 범위는 항만공사 1곳, 주요 업무 2개, 한국어 핵심 기능과 영어 주요 질문 10개다. 대상 기관과 업무는 자료 확보 가능성을 확인한 뒤 1회차에 결정한다. 세 번째 업무는 핵심 범위의 검증이 끝났을 때만 추가한다.

**2. 먼저 확정할 의사결정**

| 항목 | 결정 방법 | 완료 기준 |
|---|---|---|
| 대상 기관 | 협력 기관이 있으면 우선 검토하고, 없으면 공개 자료를 확보할 수 있는 기관을 선택 | 기관 1곳 명시 |
| 사용자 | 실제 문의 유형을 확인해 일반 민원인 또는 항만 이용 기업 중 주 사용자를 정함 | 주요 사용자와 대표 상황 3개 정의 |
| 업무 범위 | 문의 빈도, 이용자 불편, 자료 완결성, 학기 내 구현 가능성 검토 | 안내할 업무 2개와 제외 범위 기록 |
| 일정·평가 | 중간·최종 발표일, 필수 제출물, 개인 기여 평가 확인 | 학교 일정에 맞춘 마일스톤 |
| 예산·실행 환경 | 팀 장비, 사용 가능한 서버, API 비용 상한 확인 | 월별 한도와 담당자 |
| 자료 검토자 | 협력 기관 담당자 또는 지도교수에게 검토 가능 범위 확인 | 요구사항·정답·최종 시연 검토 일정 |

여수광양항만공사는 검토 후보 중 하나다. 공식 사이트에서 항만시설 이용안내, 민원서식자료실, 실적증명서 발급, 자주 묻는 질문 메뉴를 확인했다. 실제 수집할 문서의 내용·완결성·최신성은 아직 검증하지 않았다. [여수광양항만공사 공식 사이트](https://www.ygpa.or.kr/hmpg/ygpa/main.do).

업무 후보는 ① 항만시설 이용·신청 안내 ② 증명서 발급 절차 ③ 견학·방문 관련 안내로 두고, 이 중 자료가 충분한 2개를 첫 회차에 선택한다. 기관이 다르면 업무 체계와 규정을 새로 확인한다. 협력 기관이 확정되지 않더라도 공개 자료 기반 시제품 개발을 진행하고, 관계자 검토 여부를 결과에 명시한다.

**3. 사용자가 경험할 흐름**

1. 사용자가 “항만시설을 이용하려면 어떤 절차가 필요한가요?”라고 질문한다.
2. 시설 종류나 신청 목적에 따라 안내가 달라지면 챗봇이 필요한 조건을 묻는다.
3. 해당 기관·업무·적용 시점에 맞는 공식 문서에서 근거를 찾는다.
4. 요약, 이용 대상, 절차, 필요 서류를 질문에 맞게 제시한다.
5. 사용자는 출처를 눌러 원문과 관련 절을 확인하고, 공식 신청 화면으로 이동한다.
6. 근거가 부족하거나 문서가 충돌하면 확인이 필요한 내용을 설명하고 공식 문의 경로를 안내한다.

답변에 표시할 정보는 ‘질문에 대한 결론 → 필요한 절차·조건 → 문서 제목·URL·절 또는 페이지 → 문서 시행일/수정일(확인 가능할 때)·수집일’이다. 수집일과 시행일은 다른 의미로 저장한다.

예시 질문은 기능 설계를 위한 가상 질문이며, 특정 업무의 실제 신청 조건을 확정한 내용이 아니다.

**4. 기능 우선순위와 완료 조건**

| 우선순위 | 기능 | 완료 조건 |
|---|---|---|
| 1차 필수 | 공식 문서 등록·검색 | 출처와 업무 분류를 갖춘 문서에서 관련 근거 검색 |
| 1차 필수 | 근거 기반 한국어 답변 | 주요 사실과 절차가 인용 문서의 내용과 일치 |
| 1차 필수 | 출처 확인 | 답변에서 공식 원문과 근거 위치를 열 수 있음 |
| 1차 필수 | 조건 확인·답변 보류 | 모호한 질문에는 추가 질문, 근거 없는 질문에는 추측 없이 안내 |
| 1차 필수 | 웹 대화 화면 | 질문 입력, 응답 상태, 출처, 오류 안내, 새 대화 지원 |
| 최종 필수 제안 | 문서 갱신 | 새 버전 등록 후 이전 버전이 현재 질문의 근거로 선택되지 않음 |
| 최종 필수 제안 | 영어 주요 시나리오 | 주요 질문 10개에서 한국어와 같은 근거로 답하며 기관명·서류명·수치 유지 |
| 최종 필수 제안 | 평가·운영 기록 | 검색 근거, 모델 설정, 응답 시간, 사용량, 실패 유형 확인 |
| 선택 확장 | 관리자 웹 화면 | 개발용 등록 스크립트를 관리자 화면으로 확장 |
| 선택 확장 | 검색 결과 재정렬 | 검색 실패 분석 결과 필요할 때만 적용하고 성능 비교 |
| 선택 확장 | 추가 언어·업무 | 핵심 범위의 검증과 최종 발표 준비 이후 추가 |

학기 중 기본 범위는 공개 자료를 이용한 안내와 공식 신청 페이지 연결로 잡는다. 민원 접수 대행, 본인인증, 개인 신청 내역 조회, 결제, 실시간 선석·선박 현황은 별도 연동과 요구사항이 생길 때 검토한다. 원본의 24/7은 기대효과이며, 실제 상시 서비스 수준은 배포 후 가동 시간·장애 기록으로 별도 입증한다.

**5. 데이터 준비 계획**

첫 2회차에는 공식 문서 10~20건을 초기 확보 목표로 삼는다. 문서 수보다 선정한 업무의 질문에 필요한 근거가 빠짐없이 있는지를 우선한다. FAQ, 업무 안내, 신청 서식 안내, 관련 규정 순서로 검토하고, 각 문서에 연결된 원문을 추적한다. 자동 수집기 개발은 초기 범위에서 제외하고 검토한 문서 목록을 직접 등록한다.

| 기록 항목 | 목적 |
|---|---|
| 문서 ID, 제목, 원문 URL, 제공 기관 | 출처와 기관 구분 |
| 업무 분류, 적용 대상, 언어 | 질문에 맞는 범위 선택 |
| 게시·수정일, 시행일, 수집일 | 적용 시점과 확인 시점 구분 |
| 원문 파일, 내용 해시, 문서 버전 | 변경 탐지와 과거 실험 재현 |
| 절 제목, 페이지, 청크 ID | 답변에서 정확한 근거 위치 표시 |
| 추출 오류·검토 상태 | 잘못 읽힌 표나 숫자가 검색에 들어가는 것을 방지 |

수집 후에는 메뉴·광고·중복 문구를 정리하고 제목·조항·절차 단위로 나눈다. 표에서는 대상·금액·조건·단위를 함께 보존한다. PDF/HWP/스캔 자료는 처음 몇 건을 직접 확인하여 추출 품질을 판정하고, 초기에는 확인 가능한 공식 HTML과 텍스트 문서를 우선한다.

문서 안의 명령문이나 외부 링크는 참고 데이터로만 취급한다. 검색된 문서 내용이 시스템 설정이나 실행 권한을 변경하지 못하게 설계한다. 자료가 불완전하거나 날짜가 확인되지 않으면 해당 상태를 기록한다. 담당자의 확인 없이 문서 개정 시점이나 우선순위를 추정하지 않는다.

공동 작업 때 선정한 원문 목록의 변경을 확인하는 운영 절차를 제안한다. 변경 문서는 검토 후 새 색인으로 교체하고, 실패하면 기존 버전을 유지한다. 자동 갱신 예약 기능은 선택 확장으로 둔다. 평가에는 문서 버전이 고정된 사본을 사용한다.

**6. 시스템 구성과 기술 선택**

문서 준비 흐름: 공식 자료 → 텍스트 추출·검토 → 문단 분할 → 임베딩 생성 → 검색 저장소 등록.

사용자 응답 흐름: 질문 → 기관·업무·조건 확인 → 관련 문서 검색 → 근거 충분성 판단 → 답변 또는 추가 질문·확인 불가 안내 → 출처 표시.

| 구성 | 초안 선택 | 선정 이유·확인 사항 |
|---|---|---|
| 화면 | 팀이 익숙한 웹 기술 또는 간단한 HTML·JavaScript | 채팅과 출처 열람에 집중. 프레임워크 신규 학습 비용을 확인하고 결정 |
| 서버 | Python + FastAPI 후보 | 문서 처리와 검색 코드를 연결하는 API 서버로 검토 |
| 데이터 저장 | PostgreSQL + pgvector 후보 | 팀이 설치·운영할 수 있을 때 채택. 첫 회차에 실행해 보고 환경 구성을 확정 |
| 생성·임베딩 모델 | 한국어 지원 모델/API 각 1개부터 | 개발 질문으로 품질·속도·실제 사용료 비교 후 선택 |
| 초기 검색 | 벡터 검색 | 작동하는 기준 시스템과 평가 결과를 먼저 확보 |
| 개선 검색 | 한국어 키워드 검색 + 벡터 검색 | 기관명·서식명·조항 번호 검색 실패가 있을 때 비교 실험 |
| 실행 환경 | 팀이 운영 가능한 단일 서버부터 | 설치 재현, 비밀키 관리, 장애 복구가 가능한 환경 선택 |

FastAPI는 Python API 개발 프레임워크이며, pgvector는 PostgreSQL에서 벡터 검색을 지원한다. pgvector 문서에는 PostgreSQL 전문 검색과 결합하는 방식도 설명되어 있다. 한국어 키워드 검색은 실제 질의의 띄어쓰기·복합명사·기관명 처리 결과를 따로 검증한다. [FastAPI 공식 문서](https://fastapi.tiangolo.com/), [pgvector 공식 문서](https://github.com/pgvector/pgvector).

새 LLM 학습이나 파인튜닝은 기본 범위에 넣지 않는다. 첫 모델의 검색·답변 오류를 분류한 뒤 개선이 필요한 계층을 선택한다. 검색 점수를 곧바로 ‘답변 신뢰도 95%’처럼 표시하지 않고, 답변 가능 기준은 개발 질문으로 조정한다.

**7. 12회차 일정**

아래 일정은 주 1회씩 3개월 동안 작업하는 약 12회를 기준으로 한다. 실제 달력과 학교 발표일에 맞춰 배정하고, 휴강·시험으로 1~2회가 줄면 관리자 화면·추가 업무·검색 고도화를 먼저 축소한다.

| 회차 | 수행할 일 | 산출물·완료 기준 |
|---|---|---|
| 1 | 기관·업무 선택, 역할 배정, 저장소·실행 환경 확인 | 기관 1곳·업무 2개, 1쪽 기획 초안, 기본 화면·서버 실행 |
| 2 | 문서 10~20건 검토, 대표 질문 20개, 검색·화면 병행 제작 | 근거가 연결된 질문 목록, 문서 등록, 질문·답변 화면 초안 |
| 3 | 문서 검색·모델 호출·웹 화면 연결 | 문서 5~10건으로 질문→근거→답변 전체 흐름 작동 |
| 4 | 출처 링크·근거 위치, 문서 처리 보완, 평가 세트 분리 | 답변에서 실제 근거 확인, 개발/최종평가 질문 확정 |
| 5 | 조건 확인·답변 보류, 업무 범위 완성 | 주요 업무 2개와 예외 질문 처리 |
| 6 | 중간 시연, 개발 질문 평가, 오류 원인 분류 | 한국어 1차 완성본, 초기 수치와 개선 우선순위 |
| 7 | 가장 큰 오류 원인 한 가지 개선, 문서 재등록 기능 | 기준 시스템 대비 개선 결과, 문서 갱신 흐름 |
| 8 | 핵심 기능 통합·안정화, 개정·폐기·충돌 문서 점검 | 한국어 핵심 기능 동결, 설치·실행 재현 |
| 9 | 영어 주요 질문 10개, API 장애 대응, 최종 설정 고정 | 영어 시나리오와 오류 안내 검증, 최종평가 준비 |
| 10 | 보관한 최종평가 세트 실행, 소규모 사용자 실험 | 정답·출처·응답 시간·비용·탐색 시간 결과 |
| 11 | 배포·재시작 확인, 보고서·발표자료·영상 완성 | 실행 가능한 시연본, 제출물 초안, 영상 예비본 |
| 12 | 리허설, 핵심 오류 수정, 인수인계 | 최종 보고서·발표자료·소스·데이터 목록·평가 결과 |

3회차에 전체 흐름이 연결되지 않으면 문서를 5건으로 줄여 연결 문제를 먼저 해결한다. 6회차에 검색과 출처 표시가 불안정하면 검색 고도화와 관리자 화면을 보류한다. 8회차 이후 한국어 핵심 기능을 확대하지 않고, 9회차에 영어와 예외 처리를 포함한 최종 설정을 고정한다. 최종평가 후 수정이 생기면 영향을 받은 결과를 다시 측정하고 버전을 구분한다.

**8. 6명 역할 분담과 주 1회 협업**

| 작업 조 | 구성과 주 책임 | 책임 산출물 |
|---|---|---|
| A조: 기획·데이터·평가 | 1번: 업무·자료 / 2번: 정답·평가 | 문서 목록, 요구사항, 평가 질문·정답, 결과 분석 |
| B조: RAG·서버 | 3번: 문서 처리·검색 / 4번: API·답변 제어 | 검색·답변 파이프라인, 문서 등록, 갱신·오류 처리 |
| C조: 화면·실행 환경 | 5번: 채팅·출처 화면 / 6번: 배포·사용성 | 웹 화면, 서버 실행·재시작, 사용자 실험·시연 |

번호는 역할 예시이며, 경진대회에서 맡았던 역할과 주력 기술을 확인하여 배정한다. 각 조의 두 명은 상대 코드·자료를 확인하고 다른 조와 연결되는 부분을 함께 검토한다. 팀장 1명은 여섯 명 중에서 겸임하며 일정과 결정 기록을 맡는다. 발표·보고서는 모든 구성원이 자신의 실험과 구현 내용을 작성한다.

회당 3시간을 쓸 수 있다는 가정의 운영 예시는 ‘15분: 오늘의 완료 조건 확인 / 120분: 세 조 병행 작업 / 35분: 통합·시연·오류 수정 / 10분: 다음 작업과 결정 기록’이다. 실제 확보 시간이 확인되면 이 배분을 조정한다. 개인 과제가 다음 주 통합의 필수 전제가 되지 않게, 매번 종료 전에 연결된 결과를 저장한다.

첫 회차에 API 입출력과 문서 메타데이터 형식을 함께 정한다. 모듈이 완성될 때까지 다른 조가 기다리지 않도록 화면과 서버는 같은 예시 응답으로 시작한다. 문서 제목·출처 URL·근거 위치가 포함된 응답 형식을 3회차 연결 전까지 고정한다. 보고서용 화면 캡처와 실험 기록은 각 회차 종료 때 짧게 남긴다.

**9. 성능과 사용성 평가**

평가는 개발 중에 사용하는 질문과 최종 결과 보고용 질문을 분리한다. 제안 규모는 한국어 60문항으로, 답변 가능한 질문 40개·조건이 부족한 질문 10개·근거가 없는 질문 10개다. 여섯 명이 각 10개씩 초안을 만들고 A조가 중복과 근거를 검토한다. 각 유형을 절반씩 나누어 개발용 30개와 최종평가용 30개를 만든다. 같은 질문의 바꿔 쓰기 버전이 양쪽에 섞이지 않도록 묶어서 분리한다. 최종평가 문항은 설정 조정에 사용하지 않고 평가 담당자가 보관한다.

정답에는 기대 응답 유형, 필수 사실, 근거 문서·절·적용일을 기록한다. 질문과 정답은 사람이 원문을 대조하고, 가능하면 기관 담당자 또는 지도교수에게 주요 업무의 정답을 검토받는다. 검토가 불가능하면 팀 검토 범위와 한계를 보고서에 명시한다.

| 지표 | 측정 방식 | 제안 목표 |
|---|---|---|
| 근거 검색 성공률 | 답변 가능한 질문 중 상위 5개 검색 결과가 필요한 근거를 모두 포함한 비율 | 90% 이상 |
| 답변 정답률 | 답변 가능한 질문 중 필수 사실을 충족하고 중대한 잘못된 주장이 없는 비율. 답변 보류도 실패로 계산 | 85% 이상 |
| 인용 정확성 | 인용한 사실 중 해당 출처가 실제로 뒷받침하는 사실의 비율 | 95% 이상 |
| 근거 없는 질문 대응 | 근거 없는 질문에 추측 답변 없이 확인 불가를 알린 비율 | 90% 이상 |
| 조건 확인 적절성 | 모호한 질문에서 답변에 필요한 조건을 정확히 물은 비율 | 90% 이상 |
| 응답 시간 | 질문 전송부터 전체 답변 수신까지 p50·p95 기록 | p95 10초 이내를 초기 목표로 검토 |
| 사용성 | 같은 난이도의 과제를 홈페이지 검색과 챗봇으로 수행한 시간·성공률 비교 | 성공률을 유지하며 탐색 시간 단축 |

수치는 달성 결과가 아니라 지도교수·팀과 조정할 초기 목표다. 최종평가의 답변 가능한 질문은 20개이므로 검색 90%는 18/20개, 정답 85%는 17/20개에 해당한다. 예외 유형별 질문은 5개이므로 목표 90% 이상을 만족하려면 5/5개가 성공해야 한다. 분모와 성공 건수를 함께 보고하고, 작은 표본의 결과를 실제 전체 민원 대응 성능으로 일반화하지 않는다. 짧은 답만 하거나 답변을 모두 거절하는 방식이 유리해지지 않도록 정답률과 미답변률도 함께 본다.

같은 질문·원문 버전·생성 모델을 사용하여 ① 검색 없는 LLM ② 기본 벡터 RAG ③ 개선 RAG를 비교한다. 개발 세트로만 설정을 조정한 뒤 최종평가를 수행한다. 검색 방식 비교에서는 생성 설정을 동일하게 유지하고, 여러 요소를 바꾸면 어느 요소가 달라졌는지 명시한다.

영어 평가는 한국어 질문 10개의 대응 시나리오로 구성한다. 5개는 개발 점검에, 5개는 최종 점검에 사용한다. 별도의 독립 표본으로 합산하지 않고, 같은 업무를 두 언어로 수행하는 일관성을 확인한다. 문서 내부 지시문, 폐기 문서, 충돌 문서, API 장애 시나리오는 별도 회귀 점검 목록으로 관리한다.

사용자 실험은 학생 등 5~10명에게 익숙하지 않은 과제를 제시하는 소규모 형성 평가로 시작한다. 홈페이지와 챗봇 과제의 순서를 바꾸고 유사 난이도 과제를 사용해 학습 영향을 줄인다. 실제 항만 이용자가 참여하지 못하면 실제 현장 검증으로 표현하지 않는다.

**10. 비용과 운영 준비**

기본 비용 항목은 생성 모델 호출료, 임베딩 생성료, 서버·DB·저장소 비용이다. 모델 가격과 무료 제공 범위는 선정 시점의 공식 가격을 확인하고, 개발 질문을 실제 실행한 사용량으로 계산한다.

월 예상 비용 = 월 질문 수 × 질문당 평균 모델 비용 + 신규·변경 문서 임베딩 비용 + 서버·DB·저장소 비용.

질문당 모델 비용에는 입력·출력 토큰과 재시도·번역·재정렬 등 추가 호출을 포함한다. 개발 실험 비용과 서비스 운영 비용을 구분한다. 정해진 예산의 알림 기준과 호출 한도를 두고, API 키는 서버에서 관리한다.

시연 전에는 네트워크·API 실패 시 안내, 요청 시간 제한, 로그 최소 수집, 관리자 문서 등록 권한, 재시작, 원문 갱신 후 복구를 확인한다. 사용자의 개인 민원 서류 업로드 기능은 기본 범위에 포함하지 않는다.

**12. 최종 제출물과 시연 구성**

최종 제출물은 실행 가능한 웹 시제품, 소스코드와 설치 안내, 요구사항·설계 문서, 원문 목록과 데이터 처리 절차, 평가 질문·정답·결과, 최종 보고서, 발표자료, 시연 영상으로 구성한다. 외부 문서의 재배포가 어려우면 원문 URL과 재현 절차를 제공한다.

5분 시연 예시는 ① 사용자 문제 30초 ② 근거가 있는 업무 질문 60초 ③ 조건 확인과 근거 없는 질문 대응 60초 ④ 문서 갱신 또는 영어 질문 60초 ⑤ 비교 실험·사용성·한계 90초다. 영상 예비본을 준비하고 실제 실행과 녹화 화면을 구분한다.

발표의 논지는 “어떤 민원 불편을 다뤘는가 → 어떤 공식 자료를 사용했는가 → 어떻게 답을 찾는가 → 기존 방식보다 무엇이 얼마나 달라졌는가 → 어떤 질문은 아직 처리하지 못하는가”로 구성한다.

**13. 첫 작업일에 할 일**

1. 정확한 마감일·회당 작업 시간·각자의 주력 기술·예산·학교 평가표를 기록하고 2명씩 세 조를 배정한다.
2. A조는 대상 기관 후보의 공개 자료를 비교하고, 자료를 확보할 수 있는 기관 1곳·업무 2개를 제안한다.
3. B조는 저장소와 서버·검색 저장소 실행을 확인하고, 문서 1건을 읽는 작은 기능을 만든다.
4. C조는 질문 입력·답변·출처 확인 화면을 만들고 예시 응답으로 작동시킨다.
5. 함께 업무 범위와 API 응답 형식을 확정하고, 실제 실행 결과를 공유한다.
6. 문제·사용자·범위·데이터·검증 방법을 담은 1쪽 기획 초안을 남긴다. 다음 회차에는 대표 질문 20개와 문서 10~20건을 확보한다.

첫 작업일의 완료 상태는 ‘기관 1곳·업무 2개·조별 담당자·실행되는 화면과 서버·공통 응답 형식·다음 회차 완료 조건’이 정리된 상태다.
