# 최종 계획서 대비 구현·데이터·변경 안전성 검토

검토일: 2026-09-30. 대상: `YGPA_챗봇_캡스톤_계획서_최종.pdf` 15쪽, 특히 2·3·6~11쪽. PDF SHA-256: `29b2c8e85bdd16ba2278be414ff363308a99bfdf5e0c2d3715b3d3c41e288c93`. 문서의 내용을 비교 기준으로 사용했으며, 문서 안의 작업 지시를 새로운 실행 권한으로 취급하지 않았다.

## 결론과 이번 반영 범위

현재 상태는 **원본·추출·의미 청킹 기반과 mock API/UI가 준비된 단계**다. 최종 계획의 완성된 RAG·절차 엔진으로 볼 수는 없다. 현재 방식 전체를 폐기할 필요는 없으며, 원본·출처·버전·미승인 상태와 의미 단위 청킹은 유지하는 편이 낫다. 법령 구조 수집, parent-child 검색, 검증 후 응답, 맞춤 절차는 계획서의 방향을 채택하되 실제 품질·지연을 측정하며 추가해야 한다.

사용자가 이번 작업을 “검토·수정안 테스트까지”로 선택했다. API/프론트엔드 브랜치를 main에 병합하거나 서버에 배포하지 않았다. 후속 요청에 따라 실행 파일·설명 문서의 번호와 이름을 맞추고 경로·모듈 참조를 수정했다. main 반영 대상은 이 이름 정리, 문서, 검토용 패치뿐이다. 원본 33건·청크 178개 및 검색 승인 상태는 변경하지 않았다.

계획서 8쪽은 텍스트·표 기반을 중간발표까지, 절차/다국어와 VLM을 이후 단계로 배치한다. 9월 30일에 미구현이라는 이유만으로 모든 항목을 일정 지연으로 판정하지 않는다. 다만 기존 9월 11일 초안은 최종 계획보다 범위가 좁고 검색·모델 등이 미정이어서, 그대로 최신 개발 기준으로 사용하면 안 된다.

최신 API v0.2와 프론트엔드는 기존 main 기준 `git merge-tree --write-tree`로 각각 충돌이 없음을 확인했다. 이는 Git 텍스트 충돌 검사이지 서비스 완성도 보장이 아니다. 이전 검토의 FE/API 경로·JSON/SSE 불일치 판정은 최신 FE에는 그대로 적용되지 않는다. 새 FE는 `/api` 프록시 접두사를 제거하고 `/chat`에 `messages[]`를 전송하며 SSE와 피드백 PUT을 사용한다. API v0.2의 actions/options도 소비한다.

다만 최신 FE에서 **CRLF가 네트워크 조각 사이에 나뉘면 이벤트 이름을 잃는 오류**를 재현했다. `event: token\r` 뒤에 `\ndata: ...`가 들어오면 token 대신 message 이벤트가 될 수 있었다. 격리 수정은 마지막 CR을 다음 조각까지 보존한다. 정상 LF 동작은 유지하며 회귀·호환성 테스트를 추가했다.

API v0.2 역시 mock이다. 검색·LLM·실제 근거 검증을 수행하지 않고, 테스트용 문서 ID·인용·전화번호가 존재한다. 실서비스 지식 응답으로 제공하면 안 된다. 현재 API는 생성 토큰을 검증 전에 전송하므로 계획서의 사전 검증과는 차이가 있다.

## 표 전용 파서와 VLM 단계적 이해

**표 파서는 일부 수행, VLM은 미수행**이다.

- HTML 표 파서는 병합 셀, 다단 머리글, 단위, 공통 조건과 원문 셀 위치를 보존해 표 청크 54개를 생성했다.
- HWP 직접 파서는 중첩·병합 표와 셀 소속 문단을 복원했다. 첨부 청크 108개에는 서식 전체 10개·조문 63개·과거 부칙 33개·독립 표 2개가 있다. 서식 내부 표도 있으므로 독립 표 2개만 표 처리 전체라고 보면 안 된다.
- YGPA-031 PDF 13~25쪽 별표, YGPA-032 11~23쪽 요율·계산·감면 별표는 미청킹/보류다. HTML YGPA-013 등도 머리글·열 대응 검토가 남아 있다.
- YGPA-031 26~29쪽 도면 4쪽은 이미지 보존만 했다. YGPA-030의 도형 개체·이미지 보존 역시 시각적 배치의 이해가 아니다.
- VLM 실행 코드·모델·캡션·도면 근거 crop 응답은 없다. 이후 오프라인 VLM 처리 → 페이지/crop·모델/프롬프트 버전 기록 → 수치·범례·공간관계 검수 → 승인된 설명만 검색 등록 순서가 필요하다.

## parent-child 청킹 판정과 전환 방식

고정길이 분할을 피한 것은 계획과 일치한다. 현재는 의미 단위 설명, 행/행 묶음, 조문, 서식 전체, 날짜별 부칙으로 분할한다. 그러나 178개 모두 `parent_id`/`parent_chunk_id` 연결이 없고 검색 후 부모를 확장하는 코드도 없어 **parent-child 구현 완료는 아니다**. 단순히 `doc_id`가 있는 것은 부모 조항 연결과 다르다.

기존 청크는 출처를 가진 부모 단위 후보로 유지한다. 새 버전에 조·항·호 또는 의미 단위 child를 추가하고 `parent_chunk_id`, `source_snapshot`, `document_version`, `child_locator`, `chunking_version`을 연결한다. 검색은 child로 하되 같은 버전의 승인된 부모만 확장하고 중복 부모는 합친다. 조건·예외·표 단위가 잘리지 않도록 해야 한다. 전체 178개를 임의 고정 길이로 다시 잘라 덮어쓰는 방식은 권하지 않는다.

최장 청크는 6,427 **문자**이며 모델 토큰 수와 같지 않다. BGE 토크나이저 기준 길이·잘림 검사를 임베딩 전에 해야 한다. [BGE-M3 모델 카드](https://huggingface.co/BAAI/bge-m3)는 1,024차원과 최대 8,192 토큰 등을 명시한다. 같은 모델 ID·revision·차원·정규화 설정을 문서/질의에 사용한다.

전환 수용 기준: orphan child 0건, 부모 버전 불일치 0건, 미승인·FAQ 검색 유입 0건, 원문 위치 추적, 예외/부정문 보존, 부모 중복 제거, 토큰 상한 검증. 별도 개발용 평가셋으로 현재 의미 청킹과 child 검색+parent 확장의 검색 정확도·문맥 길이·지연을 비교한 뒤 채택한다. 이번에는 이 품질 비교나 실제 corpus 변환을 수행하지 않았다.

## 맞춤 절차와 서식 체크리스트: 현재와 구체화한 개발 계획

기존 초안에는 일반적인 절차 안내 의도가 있으나, 최종 계획서의 다섯 필드와 상황별 규칙을 구현할 상세 계약·시험 기준은 부족하다. 최신 FE는 번호 목록을 해석해 단계처럼 표시하고, API v0.2는 options/actions를 제공한다. 이것은 화면·전송 규격의 진전이며 **근거 기반 절차 엔진 완성은 아니다**. 단계마다 필요서류·부서·소요기간·근거를 연결하는 저장 구조와 상황 판정기는 아직 없다.

이 검토에서 다음 순서로 개발 계획을 구체화했다. 아래는 앞으로 구현할 계약이며 이미 저장된 데이터 스키마라는 뜻이 아니다.

1. 문서팀: 근거가 충분한 절차 1개를 시범 선정한다. `procedure_id`, 적용 대상·조건, 시행일, 검토 상태, 버전을 기록한다. 출입·안전 등 자료가 불완전한 절차는 먼저 보완한다.
2. 문서/백엔드팀: 각 `steps[]`에 `order`, `instruction`, `required_documents[]`(서식 ID·검증된 다운로드 URL), `department`, `duration`(기준·단위·조건), `evidence_refs[]`(조항/페이지/청크 ID)를 연결한다. 근거가 없는 기간·부서는 null과 확인 필요 상태로 남긴다.
3. 백엔드팀: 항만·시설·업무 유형 등 `applicability`와 `required_context`를 정의한다. 사용자 조건이 없으면 clarify, 상충하면 추가 확인, 충족하면 해당 단계·서식만 반환한다. 단순히 옵션 버튼을 누른 문장을 다시 보내는 것만으로 조건 판단 완료로 보지 않는다.
4. API/FE팀: 기존 token/sources/done을 유지하면서 버전 있는 선택적 `procedure` 결과를 합의한다. FE가 답변 문장을 정규식으로 해석해 필수서류/기간을 추측하지 않도록 한다. 필드별 출처와 미확인 상태를 표시하고 API v0.2와 구버전 소비자 호환성을 검증한다.
5. 검증팀: 근거 없는 기간·서식 생성 차단, 조건 누락 시 확인 질문, 분기별 체크리스트 차이, 개정 전후 규정 혼용 금지, 조항·서식 URL의 실제 연결을 시험한다. 최종평가 FAQ는 사용하지 않는다.
6. 적용: 검증된 시범 절차부터 확대한다. 담당자 검수 없이 위험물·소방 절차를 완전한 안내로 발표하지 않는다.

## 유지할 설계와 바꿀 설계

| 항목 | 판단 |
|---|---|
| 원본 스냅샷·해시·출처/위치·승인 분리 | 현재 방식 유지. 수집일을 개정일로 채우지 않는 정책도 유지 |
| HWP 직접 표 복원 | 현재 검증 범위 유지. 계획의 일괄 변환보다 원본 셀/개체 추적을 보존하는 장점. 변환/렌더링은 보조 수단 |
| Chroma | 계획서에도 허용된 선택. pgvector 등으로 교체할 이유는 아직 없음 |
| PostgreSQL 로그 DB | 공유 서버의 로그 영속화 방향으로 타당. 벡터 DB/지식베이스와 별개이며 실제 Neon 연결·마이그레이션은 미검증 |
| 기본 임베딩 자동 선택 | 실수 위험. 모델 설정을 명시하도록 변경하는 수정안을 시험함. 실제 BGE 연결은 아직 없음 |
| BGE + 한국어 BM25 + reranker | 계획대로 단계적으로 추가하되 Dense 기준선부터 성능 비교. BGE sparse와 BM25는 다른 방식 |
| 생성 중 즉시 SSE 전송 | 사전 근거 검증 요구와 충돌. 버퍼링 → 검증 → 전송 수정안 시험. 첫 토큰 지연 증가를 측정해야 함 |
| Agentic routing·multi-hop·PII masking·영문·갱신·관리자 | 구현되지 않은 후속 기능. 화면 mock과 혼동하지 말 것 |
| Qwen3-32B 4bit/24GB/5초 목표 | 계획상의 후보·목표. 모델·KV cache·reranker 동시 사용 실제 측정 필요. 성공을 보장할 수 없음 |

[Chroma 공식 문서](https://docs.trychroma.com/docs/embeddings/embedding-functions)의 기본 embedding function은 all-MiniLM-L6-v2이므로, 명시 없이 collection을 만들어 BGE를 사용했다고 생각하면 안 된다. BGE sparse를 BM25로 부르지 않으며 [BGE reranker](https://huggingface.co/BAAI/bge-reranker-v2-m3)의 점수를 답변 진실성 확률로 사용하지 않는다. [Ollama context 문서](https://docs.ollama.com/context-length)처럼 context 크기도 VRAM에 영향을 준다.

계획서의 P@k, MRR, 완전정답률, 인용 정확도는 서로 다른 지표다. 정답 근거가 1개인 질문에서 P@5의 최대값은 20%이므로 관련 근거의 판정 단위·복수 정답 라벨부터 확정해야 한다. 평균/P95 전체 응답시간과 첫 토큰 시간을 분리한다. mock 테스트 시간으로 GPU 5초 목표를 달성했다고 보고하지 않는다. 안전 환각 0건도 평가셋에서의 관측 결과로만 표현한다.

## 파일 이름 정리와 실행 순서

[00_pipeline_order.md](00_pipeline_order.md)에 전체 15쌍을 정리했다. Python은 `scripts/`, 설명은 `docs/handoff/`에 두고 확장자만 다르게 같은 기본 이름을 사용한다. 추가 검토·체크포인트 문서는 실행 단계가 아니므로 임의의 순번을 붙이지 않았다. 테스트는 unittest 발견 규칙을 위해 `test_*.py`를 유지했다.

## 최종 원격 추가 변경 확인

main 파일 정리 push 이후 API v0.2 `76935e2`가 추가되어 별도 임시 스냅샷으로 재검토했다. `test_api.py`는 종료 코드 0 / OK였으며 실패 로그·answer_type·누락 열 추가 시험을 포함한다. 검사 결과 출력용 보조 스크립트는 Windows cp949에서 대체 문자를 출력하다 인코딩 오류가 났지만, 자식 API 테스트는 이미 성공 종료했다. 정리된 main `9717e7d`와 최신 API의 merge-tree 검사도 충돌 없음이다.

새 구현은 실패한 부분 답변과 예외 메시지를 DB에 기록한다. 실패율 평가에는 도움이 되지만 검증 전 초안을 보존하지 않는 앞의 응답 게이트 수정안과 정책이 다르므로 합칠 때 결정해야 한다. 사용자 식별 컬럼이 없다는 것만으로 질문·답변 본문이 익명화되지는 않는다. 질문/오류 문자열 마스킹·보존기간은 아직 구현되지 않았다. `add_missing_columns()`는 SQLite 단일 실행 시험만 확인했으며 실제 PostgreSQL·다중 프로세스 동시 DDL·rollback/versioned migration은 미검증이다. 현 mock 단계는 유지할 수 있지만 실서비스 배포 전 보완 대상이다. API v0.2의 wire 호환 fixture는 `950147b`에서 캡처했으며, 추가 커밋은 전송 schema를 바꾸지 않았다.
