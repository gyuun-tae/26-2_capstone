# 20. 개발용 질문 묶음으로 실제 RAG 측정

실제 민원인 말투로 쓴 개발용 질문 31개로 실제 모드(GPU 서버 + Neon)를 돌려, 검색·응답 유형·버튼·근거 번호·속도를 잰다. **FAQ(최종 평가 전용)는 쓰지 않는다.** 지시문·검색을 바꿀 때마다 같은 묶음으로 전후를 비교한다.

```powershell
cd src/api
uv run python eval_dev.py --label <이름>          # 전체 30개, 약 2~3분
uv run python eval_dev.py --only a01,c01          # 일부만
```

- 설정: 저장소 루트 `.env`의 `DATABASE_URL`·`GPU_URL`·`GPU_API_KEY`·`INDEX_VERSION` (`try_real.py`와 같음). GPU 서버 서비스가 켜져 있어야 한다.
- 대화 로그는 남기지 않는다. 결과: `evaluation/reports/dev_eval_<날짜>_<이름>.json` (질문별 답변 전문 포함).

## 질문 묶음 `evaluation/datasets/dev_questions_v1.jsonl`

| 묶음 | 개수 | 기대 |
|---|---:|---|
| answer | 19 | 절차·서식·시설 질문. 정답 문서 검색, 맞는 버튼 (a19: 이용 제한 공지) |
| clarify | 5 | 대상이 여럿인 질문 ("사용료", "출입증 신청", "예약", "여객선터미널 위치", "부두 시설 규모") |
| unknown | 5 | 자료에 없는 항만 주제 3 + 무관한 주제 2 |
| followup | 2 | 되묻기 → 선택지("체육시설", "홍보관")를 고른 이어지는 대화 |

질문마다 `expect_type`(허용 유형 목록), `expect_docs`(상위 5개 안에 하나라도 있으면 적중), `forms_required`·`forms_allowed`(서식 다운로드 버튼), `port_mis`(true/false, null이면 상관없음), 필요하면 `must_mention`(답에 꼭 들어갈 단어)을 적었다. **기대값은 API 담당이 문서 목록을 보고 쓴 초안이므로 업무·자료 담당의 검토가 필요하다.**

## 남은 일

- c05 "부두 시설 규모": 광양항 부두들만 나열하고 되묻지 않음 (여수항 근거가 상위에 없음). 여러 부두를 나열하는 답도 쓸 만해 기대값을 바꿀지 검토.
- 목록형 답(a03 실적증명서 종류 10개)은 항목마다 번호를 달지 않는다 (번호 없는 줄 합계 10).
- m02 답의 한 항목이 다른 문서(체육시설) 근거를 인용 — 문서당 2개 검색으로 다른 시설 근거가 섞일 때의 영향을 지켜본다.
- 질문 묶음 확대(40~50개)와 업무·자료 담당 검토. 검색 담당 기준선(17번)과 달리 이 묶음은 실제 말투라 더 어렵다.

### 시도하지 않았거나 남긴 것

- **c05 "부두 시설 규모"**: 검색 상위에 여수항 근거가 없어 광양항 부두만 나열한다. 근거 6개로 늘려도 그대로. 나열한 답도 근거에 맞으므로 기대값을 "answer 허용"으로 바꿀지 업무·자료 담당과 정한다.
- **확인 불가 기준 상향(0.48 → 0.52)**: 무관 질문 일부를 LLM 없이 빨리 거를 수 있지만, 실제 사용자 표현의 정상 질문이 잘릴 위험을 이 묶음으로는 잴 수 없어 보류.
- **키워드 검색(BM25) 결합**: 이 묶음의 검색 적중이 이미 26/26이라 효과를 잴 수 없다. 질문 묶음을 키운 뒤 검토.
- **DB 연결 확인(pool_pre_ping) 끄기**: 검색당 왕복 1회를 줄일 수 있지만 Neon이 쉬는 동안 끊긴 연결로 요청이 실패할 수 있어 유지.
