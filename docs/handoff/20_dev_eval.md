# 20. 개발용 질문 묶음으로 실제 RAG 측정

실제 민원인 말투로 쓴 개발용 질문 30개로 실제 모드(GPU 서버 + Neon)를 돌려, 검색·응답 유형·버튼·근거 번호·속도를 잰다. **FAQ(최종 평가 전용)는 쓰지 않는다.** 지시문·검색을 바꿀 때마다 같은 묶음으로 전후를 비교한다.

```powershell
cd src/api
uv run python eval_dev.py --label <이름>          # 전체 30개, 약 2~3분
uv run python eval_dev.py --only a01,c01          # 일부만
```

- 설정: 저장소 루트 `.env`의 `DATABASE_URL`·`GPU_URL`·`GPU_API_KEY`·`INDEX_VERSION` (`try_real.py`와 같음). GPU 서버 서비스가 켜져 있어야 한다.
- 대화 로그는 남기지 않는다. 결과: `evaluation/reports/dev_eval_<날짜>_<이름>.json` (질문별 답변 전문 포함).

## 질문 묶음 `evaluation/datasets/dev_questions_v1.jsonl`

| 묶음 | 개수 | 기대 |
|---|---:|---|
| answer | 18 | 절차·서식·시설 질문. 정답 문서 검색, 맞는 버튼 |
| clarify | 5 | 대상이 여럿인 질문 ("사용료", "출입증 신청", "예약", "여객선터미널 위치", "부두 시설 규모") |
| unknown | 5 | 자료에 없는 항만 주제 3 + 무관한 주제 2 |
| followup | 2 | 되묻기 → 선택지("체육시설", "홍보관")를 고른 이어지는 대화 |

질문마다 `expect_type`(허용 유형 목록), `expect_docs`(상위 5개 안에 하나라도 있으면 적중), `forms_required`·`forms_allowed`(서식 다운로드 버튼), `port_mis`(true/false, null이면 상관없음)를 적었다. **기대값은 API 담당이 문서 목록을 보고 쓴 초안이므로 업무·자료 담당의 검토가 필요하다.**

### 기준선에서 찾은 문제와 고친 방법

| 질문 | 문제 | 고친 방법 |
|---|---|---|
| c01 사용료 | 근거에 체육시설·항만시설이 다 있는데 "확인 불가" | 지시문 6번: 답하기 전 근거 제목으로 대상이 하나인지 확인, 여럿이면 되묻기. 질문 끝 요약에 "대상이 여럿이면 되묻기" |
| c02 출입증 신청 | 발급 하나로 단정 + 관계없는 Port-MIS 버튼 | 위와 같음 → 신규/기간연장 선택지 |
| c03 예약 | 근거 5개가 모두 체육시설이라 되물을 수 없음 | **검색 결과를 문서당 2개까지** (`app/search.py` `diversify`) → 체육시설·홍보관·항만안내선이 함께 들어옴 |
| m02 "홍보관" | 앞에서 되물은 문장을 그대로 반복 | 짧은 답은 LLM에게도 "앞 질문 + 사용자의 선택"으로 합쳐 보냄 (`effective_question`) |
| u04 운임 | 본문은 확인 불가인데 정리 줄은 answer | 본문이 확인 불가 문구면 unknown으로 처리 |
| a15 업체 등록 | 서식 이름은 안내했는데 버튼을 안 고름 | 질문 끝 요약에 "작성할 서식을 안내했으면 그 번호를 forms에" |

## 남은 일

- c05 "부두 시설 규모": 광양항 부두들만 나열하고 되묻지 않음 (여수항 근거가 상위에 없음). 여러 부두를 나열하는 답도 쓸 만해 기대값을 바꿀지 검토.
- 목록형 답(a03 실적증명서 종류 10개)은 항목마다 번호를 달지 않는다 (번호 없는 줄 합계 10).
- m02 답의 한 항목이 다른 문서(체육시설) 근거를 인용 — 문서당 2개 검색으로 다른 시설 근거가 섞일 때의 영향을 지켜본다.
- 질문 묶음 확대(40~50개)와 업무·자료 담당 검토. 검색 담당 기준선(17번)과 달리 이 묶음은 실제 말투라 더 어렵다.
